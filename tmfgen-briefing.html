Konteks

Membangun backend TMF ODA manual itu mahal

Repo ini sudah menyimpan spec resmi dari 100+ komponen TM Forum ODA di documents/. Setiap komponen yang dibangun tangan membuka celah yang sama.

Biaya membangun manual

Entity, DTO, controller, wiring event/hub, house filter, soft-delete — semuanya ditulis ulang tiap komponen, memakan waktu developer yang sama berulang kali.

Konsistensi menurun

Semakin banyak servis dan developer, semakin mudah pola berbeda-beda antar servis — sulit dipertahankan lewat review manual saja.

Spec TMF terus berubah

Update versi spec berarti mengulang penyesuaian manual di semua servis yang memakainya, dengan risiko human error tiap kali.

Jawaban tmfgen

Generate deterministik dari spec resmi: pola yang sama di semua servis, hasil bisa direproduksi, dan diverifikasi lewat test snapshot — bukan ditebak-tebak.

Konteks

Apa itu tmfgen

Command-line generator kode, bukan asisten AI di jalur generate-nya.

  • Input: satu spec OpenAPI/Swagger milik komponen TM Forum ODA.
  • Output: backend NestJS + TypeORM yang siap jalan — entity, DTO, controller, service, wiring hub/listener/event.
  • Jaminan inti: spec input yang sama selalu menghasilkan kode yang identik byte-per-byte. Diverifikasi lewat harness golden-snapshot, bukan sekadar diasumsikan.
  • Bukan pengganti developer: logika bisnis custom tetap ditulis manual, di titik ekstensi yang sengaja tidak pernah disentuh generator (lihat bagian batasan).

Kenapa deterministik itu penting

Regenerasi ulang servis yang sama — setelah spec berubah, atau template generator diperbaiki — aman dilakukan kapan saja tanpa takut merusak logika custom yang sudah ditulis manual di titik ekstensi.

Konteks Developer

Pipeline generator: empat tahap

Urutan ini tetap — ir untuk pratinjau, scaffold sekali per servis, emit aman diulang, inject opsional untuk servis existing.

01

ir

Pratinjau

Parsing spec jadi intermediate representation tmfgen; mencetak resource, field wajib, sub-entity, warning. Tidak ada kode ditulis.

Jalankan sebelum scaffold & tiap cek dampak perubahan spec/enrichment.
→
02

scaffold

Kerangka servis

Membuat direktori servis baru: package.json, main.ts, app.module.ts, .env.example, guard/filter umum, wiring database.

Sekali per servis baru — menolak jalan kalau folder sudah ada.
→
03

emit

Generate resource

Menggenerate entity, DTO, controller, service, wiring hub/listener/event untuk tiap resource di spec.

Aman diulang — file hasil generate selalu ditimpa ulang.
→
04 · opsional

inject

Sisipkan ke servis existing

Logika sama dengan emit, tapi menyasar servis hand-written lewat deteksi konvensi + rencana dry-run.

Wajib dry-run dulu, baru --apply.
Persiapan Developer

Instalasi & konfigurasi

Sekali di awal per mesin developer.

  • Prasyarat: Node.js 18+ (dikembangkan di Node 22) dan Yarn 1.x — servis hasil generate adalah Yarn workspace yang di-pin ke yarn@1.22.22.
  • Setup sekali: masuk ke generator/ lalu install dependency generator itu sendiri.
cd generator
npm install

generator/tmfgen.config.json — menunjuk ke lokasi hasil generate:

{
  "targetRoot": "D:/project/tm-forum",
  "overrides": {},
  "portRange": [3026, 3099]
}

targetRoot lokasi semua servis · overrides jarang dipakai, diskusikan dulu · portRange cuma fallback kalau identity port bentrok.

Wrapper CLI: tmfgen

Dijalankan lewat ./tmfgen (bash/git-bash) atau tmfgen (cmd/PowerShell) dari root repo — tidak perlu cd generator atau prefix node src/cli.mjs. Bentuk lama tetap berfungsi sama persis kalau lebih terbiasa dengannya.

Menyiapkan dokumen komponen TMF

tmfgen membaca langsung struktur documents/<tmfNNN>/<versi>/ yang sudah dipakai di repo ini.

documents/tmf670/4.0.0/ ├── openapi/ ← satu-satunya input WAJIB (.yaml/.yml/.json) │ └── TMF670_..._swagger.json ├── userguide/ ← opsional — sumber untuk skill /enrichment │ └── TMF670_..._specification.pdf ├── conformance/ ← TIDAK dibaca otomatis oleh generator │ └── TMF670_..._conformance.pdf ├── postman/ ← tidak dipakai proses generate └── ctk/ ← tidak dipakai proses generate
  • Ada beberapa file mirip-spec di openapi/? tmfgen mengambil yang urutan alfabetnya paling awal dan melewati yang namanya mengandung postman — kalau ambigu, arahkan langsung ke file spec-nya.
  • PDF userguide tidak diparse otomatis oleh generator — itu tugas skill /enrichment, dibahas berikutnya.
Persiapan DeveloperSA

Enrichment: melengkapi apa yang tak ada di spec

Spec OAS sering tidak menyertakan deskripsi field yang jelas atau aturan bisnis kontekstual yang justru ada di PDF userguide (dan conformance profile).

  • Skill /enrichment <userguide.pdf> [conformance.pdf] membaca PDF, lalu cross-check ke ground truth tmfgen ir — tidak pernah mempercayai PDF saja.
  • Menulis documents/<tmfNNN>/<versi>/tmf<NNN>-enrichment.md: deskripsi field + catatan business rule.
  • Aturan keras: hanya memperkaya field yang sudah ada di IR (deskripsi & pengetatan mandatory) — tidak pernah menciptakan field atau resource baru.
  • Dipakai lewat -m <file> saat ir/scaffold/emit.

Contoh nyata — TMF670 Payment Method

1 resource diperkaya, 7 field mendapat deskripsi dari userguide, plus catatan business rule dari conformance profile — termasuk celah AccountRef yang response-mandatory tapi mudah terlewat kalau cuma baca OAS.

tmfgen ir documents/tmf670/4.0.0 \
  -m documents/tmf670/4.0.0/tmf670-enrichment.md
# → markdown supplement: 1 enrichment(s)
Untuk developer Developer

Alur kerja developer, langkah demi langkah

Dari dokumen siap sampai backend ter-build, dengan wrapper tmfgen di root repo.

  1. Pastikan spec bisa dimuat bersih

    documents/tmf<NNN>/<versi>/openapi/*.yaml|json harus ada; tmfgen akan berhenti dengan pesan jelas kalau ada $ref yang tidak bisa diresolusi.

  2. (Opsional, direkomendasikan) Jalankan enrichment

    /enrichment <path-userguide.pdf> untuk menghasilkan tmf<NNN>-enrichment.md.

  3. Pratinjau dengan ir

    tmfgen ir documents/tmf<NNN>/<versi> — baca ringkasan resource/field/warning sebelum menulis kode apa pun.

  4. Scaffold servis baru

    tmfgen scaffold documents/tmf<NNN>/<versi> — sekali saja per servis.

  5. Emit resource

    tmfgen emit documents/tmf<NNN>/<versi> -m <enrichment.md> — aman dijalankan ulang kapan saja.

  6. Verifikasi dengan build sungguhan

    cd <targetRoot>/<service> && yarn install && yarn build.

  7. Tulis logika custom di titik ekstensi

    <resource>.hooks.ts untuk business rule, <resource>.controller.extra.ts untuk route tambahan.

Batasan & jaminan

Apa yang tmfgen jamin — dan tidak

Penting untuk memahami batas otomasi ini sebelum menjanjikannya ke stakeholder lain.

Required field ikut OAS, bukan conformance PDF

Disengaja: OAS adalah kontrak minimum teknis; tabel mandatory di conformance profile kadang tidak sinkron dengannya. Validasi lebih ketat berisiko menolak request yang sah menurut OAS.

File bertanda GENERATED selalu ditimpa

Jangan pernah edit manual file berkomentar // GENERATED by tmfgen - DO NOT EDIT. — akan hilang diam-diam saat emit berikutnya.

Dua titik ekstensi yang aman

<resource>.hooks.ts dan <resource>.controller.extra.ts ditulis sekali dan tidak pernah disentuh generator lagi.

Field version dikelola otomatis

Field bernama persis version (root/sub-resource) di-set "1.0" saat create dan naik major/minor saat update — tanpa konfigurasi apa pun.

Untuk developer Developer

Memverifikasi hasil generate

Exit CLI yang bersih bukan bukti kode-nya benar — selalu build sungguhan.

Setiap generate

cd <targetRoot>/<service>
yarn install
yarn build   # tsc lewat nest build

Perubahan pada generator sendiri

cd generator
node tools/golden.mjs           # cek vs snapshot
node tools/golden.mjs --update  # rekam ulang, cek diff dulu
node tools/golden.mjs --case tmf736-v5

Harness ini juga menguji determinisme: generate kasus yang sama dua kali harus menghasilkan output byte-identik.
